# Архитектурные решения и ограничения

Этот документ дополняет README техническими компромиссами учебного прототипа. Код и воспроизводимая база предназначены для открытой публикации; локальные токены, сообщения и профиль браузера исключены из Git.

## 1. Интеграция amoCRM

Рабочий путь текущего демо: входящее сообщение онлайн-чата → опрос новых событий amoCRM → журнал обращений → два блока → внутреннее примечание в сделке. Альтернативно доступен приём официального вебхука `add_message` при наличии постоянного публичного HTTPS адреса. Playwright используется только при настройке или демонстрации браузера и отсутствует в исполняемом сервисе.

**Сильная сторона:** сервис не зависит от DOM amoCRM. Повторная доставка сообщения подавляется по ID.

**Ограничение:** в текущем аккаунте настроены токен приватной интеграции и автоматический опрос, но получение текста через `GET /ajax/v3/leads/{id}/events_timeline` опирается на неофициальный endpoint интерфейса amoCRM. Он может измениться. Постоянный публичный HTTPS адрес для официального вебхука не настроен. Фоновая обработка выполняется в процессе веб-сервера; при его остановке сообщение со статусом `queued` не возобновится автоматически.

**Перед реальной эксплуатацией:** очередь с повторными попытками и мониторингом, отдельная политика хранения клиентских сообщений, ограничение прав токена и проверка доступности HTTPS.

## 2. База знаний и BM25

SQLite хранит 8 учебных документов, 16 атомарных фактов, 9 алиасов и 2 правила допродажи. Документы дают поисковый контекст, а конкретные значения берутся только из `facts`. FTS5/BM25 индекс создаётся из SQLite при старте, поэтому его можно восстановить. Источник и дата проверки указаны у каждого документа.

Для этого тестового объёма важнее покрытие типовых вопросов, чем 100+ строк каталога. Векторный поиск не даёт преимущества без подготовленных качественных данных. При расширении стоит добавлять реальные короткие документы по каждой политике и товару, а не дублировать названия ради размера базы.

**Ограничение:** учебные цены и остатки вымышлены. Обновление фактов не подтягивается автоматически из каталога. Изменение документов или алиасов требует перезапуска для перестройки FTS5. Русский стемминг и BM25 улучшают поиск, но не понимают отрицания или сложные ссылки на товар из предыдущих реплик.

## 3. Понимание обращения и ответ

Сервис ищет явно названный товар по алиасам, определяет темы по словоформам и допускает в ответ только факты из документов, попавших в BM25 выдачу. Возврат, претензия и медицинский вопрос обрабатываются отдельно. Ответ остаётся черновиком.

**Сильная сторона:** локальный режим предсказуем и бесплатен; даже с AITUNNEL каждая цифра находится в SQLite и имеет источник. Модель расширяет запрос между двумя проходами BM25 и может распознать неявную потребность без буквального триггера.

**Ограничение:** текст шаблонный; сервис учитывает последние пять входящих реплик одной беседы за 24 часа, но не видит исходящие ответы менеджера. Он разрешает местоименные продолжения через последний однозначно названный товар, однако сложную смену темы может понять неверно. Для ответа по нескольким товарам одновременно нужна отдельная композиция; сейчас сервис просит уточнить товар. Уточняющие вопросы по неполным данным можно сделать более конкретными.

## 4. Подсказка о допродаже

Правило хранит основной товар, дополнение, основание, вопрос, триггеры и приоритет. Оно срабатывает только при однозначном товаре и конкретной потребности из текущей реплики. Общая фраза «для работы с таблицами» не является основанием предложить монитор; проблема с несколькими окнами является. При отсутствии основания менеджер получает просьбу уточнить задачу без названия дополнения. Жалобы, возвраты и медицинские вопросы исключают продажу. Подсказка отдельно обозначает, что менеджер проверяет совместимость, цену и наличие.

**Ограничение:** наличие дополнительного товара не сверяется с живым складом; совместимость описана редакторским правилом, а не вычисляется по матрице характеристик. Для более сильной версии нужны структурированные ограничения совместимости, актуальные остатки и оценка эффективности рекомендаций по действиям менеджера.

С AITUNNEL модель предлагает гипотезу о потребности и цитату клиента, после чего сервер проверяет существование правила в SQLite. Точная цитата не является доказательством правильности вывода; поэтому ответ остаётся черновиком, а менеджер проверяет смысл рекомендации.

## 5. Интерфейс менеджера

Локальная панель автоматически показывает новое обращение, два блока и основания. В amoCRM оба блока публикуются как внутреннее примечание в сделке. Менеджер копирует клиентский текст и отправляет его вручную.

**Ограничение:** это пока отдельная панель и заметка в карточке сделки, а не нативный виджет в окне imBox. Для нативного встроенного интерфейса понадобится amoCRM JS-виджет с авторизацией к серверу и подходящими областями размещения.

## 6. Передача и демонстрация

Локальный сценарий воспроизводится из исходников через `init-db` и `serve`, без токенов и amoCRM. AITUNNEL включается только при `LLM_API_KEY`. Живая интеграция на аккаунте автора работает через опрос; новый клиент открывается кнопкой `/client` в отдельном окне и создаёт отдельную сделку. Проверены диалоги с обычными формулировками: ноутбук, большой экран, возврат, доставка, отсутствующий товар и случаи с подтверждённой и неподтверждённой допродажей. В видео нужно честно показать, какие данные учебные, где BM25, какую роль играет необязательная LLM и как два блока попадают менеджеру. Подробные команды и переменные окружения находятся в README.
